# Departure approval handover

Application provider: `server/providers/departure-reassignment/index.ts` default export. Register it in `server/providers/index.ts` after `DepartureProvider` and the other approval owners. Its dependency on departure is lazy: owners are resolved when maintenance runs, not during provider registration. It binds `departureApprovalReassignmentToken`; it is not a plugin or HTTP endpoint.

The explicit registry covers the 19 currently registered OA approval lifecycles. Each owner's public `tasksOf` is source-scoped and paged before mutation. Tasks are deduplicated by ID; original assignees behind proxy tasks are retained. Current human tasks are migrated through the owning business `action`, never approval table writes. Unknown lifecycle owners, missing current-run facts, rejected eligibility and denied record access remain blocking. Historical plugin kinds that are no longer registered are outside this contract: this adapter does not claim they were migrated. The coverage test fails when a newly registered OA module constructs an ApprovalService without a binding.

A fresh directory selects an active, independent `approval.admin` in sorted order. This means actual approval authority, not notification recipients or an arbitrary administrative duty-role row. The public authorization API resolves this actor's subjects and evaluates each owner's composite `view` grant. Only the actual collection RepositoryPolicy is supplied to the public action; no synthetic unrestricted policy is introduced. The native SDK still checks administrator authority, target identity and successor eligibility. A revoked fixed actor cannot be replaced during retry.

The installed SDK deduplicates request IDs but does **not** compare input/comment payloads. Before any SDK action, `departureReassignmentCommands` durably binds requestKey, from, to, reason and the first actor in its own audited transaction. Conflicting payloads fail before migration. Unique-key conflicts reconcile outside the failed transaction, including PostgreSQL aborted transactions. The departure executor's fixed target and request key do not substitute for this adapter boundary.

Each task uses a deterministic request ID derived from the command key and real task ID. Public action history must confirm request ID, action, actor, task, successor, override=false and comment. Every successful SDK action commits independently. A failed later task does not roll back an earlier success; retries rescan outstanding tasks and do not duplicate successful actions. Final `remaining` is an actual public rescan. The departure executor must disable accounts only when remaining is zero.

## Verification

`pnpm exec vitest run tests/logic/departure-reassignment` passed 14 tests on 2026-10-11. Five use the full isolated application, real migrations/database and installed Approval SDK: all owner bindings resolve, actual task/receipt and durable replay match, partial first success/second failure recovers without duplicate actions, inactive successors block, and concurrent same-key different-target requests cannot both migrate.

Nine unit/coverage tests exercise complete pagination, deduplication and cross-owner routing, active human task variants and proxy originals, unknown or mismatched lifecycle facts, successor qualification rejection, actual administrator selection, and missing receipts. Targeted ESLint and formatting pass. The server TypeScript check reports only concurrent assets/vendor-qualification changes outside this module; no departure-reassignment diagnostic was reported. No browser verification was performed for this server-only adapter.

## Vendor registration follow-up

After adding the shared qualification/removal owner `oa.vendorQualification`, the registered application regression again passed all 14 tests in three files (`/tmp/oa-reassignment-vendor19-final.log`, 12.24s). The first regression exposed registry ordering disagreement; the owner list now matches the explicit lifecycle registry. The vendor facade has a different argument order and is adapted explicitly; the policy-aware input type no longer intersects the three-argument execution facade. Targeted lint and the current server TypeScript check passed. These results cover registered binding and existing migration cases, not a new vendor-specific departure end-to-end scenario.
