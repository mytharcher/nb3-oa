# IT 报修模块设计

日期：2026-10-29 Asia/Singapore。[需求基线](../baseline/it-repairs.md)。当前只交付受理切片；完整闭环仍分阶段实施。

## 状态和事务

`itRepairs` 是唯一状态源。当前 lifecycle `oa.itRepair` 只开放 `draft → triage`、草稿编辑和附件归属动作；`refreshRouting` 仅供配置变更在同一事务刷新负责人待办，不对员工开放。后续十状态扩展在下一阶段补齐，不将待分诊标作终态。

新表为工单、命令回执、服务组及 File Collection。实际时间点均为 datetimeTz；新增迁移，不修改已发布历史。规则/分类使用平台版本化规则和字典，服务组按版本更新。

命令按操作者和请求键定位回执，指纹包括动作、目标、期望版本和规范化内容；上传还包括完整字节摘要。先重查当前访问权，再回放原成功结果。更新使用 lifecycle 的状态/版本条件写；审计、编号、回执、来源目标和任务 writer 与业务共用事务。读取和轮询不写库。

普通 PostgreSQL 业务命令显式使用 REPEATABLE READ，规则和日历日期在同一一致视图读取；原生账号管理锁串行化同一员工的写动作。并发序列化/死锁/唯一竞争回滚后重试整个命令，避免在旧快照内重读不存在的回执或编号行。正常版本冲突由用户显式读取最新版本后决定是否覆盖保留输入。配置日历、分类映射及恢复使用 SERIALIZABLE，拒绝两个不同操作者之间的谓词写偏差；整个命令重试后重新核对版本或分类占用，失败不保留规则、回执或审计。

## 冻结日历

平台新增 `CalendarService.captureSnapshot`，保存时区、默认星期、所有例外日期、分段时段和捕获时刻。工单保存规则值及版本身份。计算器只读冻结副本，午休/周末/例外不计入；既有审批的单段工作时间和最新日历行为保持原样。编号可显式使用同一冻结时区。

报修上午/下午时段可在 IT 服务组的工作时段抽屉维护；P1–P4 数值目标复用规则页面。日历变更只影响新提交。80% 和超时的时刻算术已验证，提醒调度与后续状态累计计时属于下一阶段。

## 权限和文件

提供员工、负责人、配置三组可编辑权限集，不自动分配给全体用户。员工只能读写本人工单；负责人只能读取当前有效授权组的已提交工单。配置权限不授予业务读取；当前员工/账号资格每次重查，配置变更即时撤销旧负责人读取并清理待办。页面、动作、数据库记录范围与字段投影分别校验；任一必要字段被拒则详情拒绝返回。

首阶段仅支持本人持有且具备资产读取权限的资产；不改变资产归属、库存或财务事实。负责人没有资产权限时只显示已关联且信息受限，不能伪造为空。明确委托报修资格和来源门面留待后续阶段。

故障附件使用原生 File Repository，磁盘私有、流式内容路由。业务 `public` 表示报修人及授权 IT 可读，不表示互联网公开。通用上传/改写/删除关闭，单文件业务命令验证 PNG/JPEG/PDF 签名或完整 UTF-8 纯文本；禁 HTML/SVG及二进制伪装，整单限额与版本推进同事务。字节检查及摘要在锁外完成，原生上传在业务事务中；回滚清理对象，失败不得留下可访问关联。内容路由每次重鉴权，响应不含存储 key/disk，不签永久公开 URL。

## 待办、通知和界面

Task Center 来源为 `oa.itRepair`，不创建审批任务或额外工作事项。仅变化的接收项调用 writer；目标解析落到来源页或待办中心自己的详情子路由。发起目录、收藏和最近使用复用现有请求目录公开键。

提交在 lifecycle 中持久化通知 effect，提交后按“工单受理事件＋单一收件人”的稳定幂等键发送安全编号和通用文案。已被原生 Notification 接受的事件保留原消息及通道，其投递重试仍由原生服务负责；新增负责人生成自己的投递身份，员工回执不重复。发送前重查当前接收资格；缺通道或无有效负责人保留失败供重试，不撤销成功工单。复用应用 `oaApprovals.inbox` 指定的站内通道；配置页提供不含业务记录的健康提示。

新建/编辑、组配置及工作时段均使用现有右侧抽屉；提交后的只读详情使用标签和值及 LongText。失败保留输入；幂等键随内容变化更新，重试沿用原键。输入未保存时禁止提交，版本冲突可读取最新版本并保留输入。列表分页、标题/编号搜索、状态过滤和日期排序使用 URL 参数；中英文和移动端复用现有组件。

## 成本和边界

- 读：分页授权查询、资格/组上下文和必要投影，不逐工单扫描授权、不写索引。
- 写：一笔业务事务；同一员工不同草稿也会串行，属于当前简化的成本。
- 提交：冻结日期集合及规则版本读取、编号行锁、负责人实际变化人数的 writer 写入，成本随日期数与负责人数量增长。
- 上传：完整摘要/内容验证 O(文件大小)，随后一笔原生存储写；持锁期间写文件的实测见[验证记录](../../records/oa/it-repairs-2026-10-29.md)。未引入上传租约或快照去重表。
- 通知：持久 effect 加原生投递重试；重启补扫复用 lifecycle jobs，每分钟有界处理 effect，未增加业务 SLA 扫描或来源跟进框架。
- 组配置：负责人集合或启停状态改变时才核对已分组工单的待办差异；只改名称、分类或工程师不刷新既有工单版本。每次配置额外读取最多 101 张匹配分类的未分组待分诊单，恢复前 100 张。
- 配置页“恢复未分组报修”调用受限 `POST /itRepairs/groups/:id/recoverRouting`，携请求键和组版本继续下一批；回执返回处理数和是否仍有下一批。它与配置保存同用一条事务路径，恢复路由、待办、逐单审计、历史及通知意图，不改变编号、首次提交、优先级、冻结规则/日历和期限。空批次不产生工单或待办写入；管理员不因此获得业务详情权限。
- 新恢复入口只处理未分组工单；已分组大队列在实际路由配置变化时仍按已有同步路径处理，大组变更的容量测量留作后续。
