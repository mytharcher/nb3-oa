# IT 报修需求与验收

日期：2026-10-29 Asia/Singapore。状态：需求草案，尚未实施。

本文面向员工、IT 服务负责人、开发及验收人员，定义从故障提交到用户确认恢复的完整业务闭环。首期目标是让员工找得到入口、IT 接得住工单、处理过程可追踪、完成结果可核实，并接入现有 OA 的待办、通知、资产和权限体系。

本文中的流程、时限及权限是新功能的建议契约；尚未由业务负责人确认的默认值集中列在第 14 节。验收用例描述未来实施后的验证要求，不代表已经执行通过。

## 1 现状与需求差异

| 事项       | 当前实现                                 | 本次目标                                               |
| ---------- | ---------------------------------------- | ------------------------------------------------------ |
| 员工报修   | 有通用申请、工作事项，无专门 IT 报修入口 | 提供结构化故障单和本人进度查询                         |
| IT 办理    | 工作事项支持分派、认领、结果确认         | 增加故障分类、优先级、维修记录、等待原因及服务时限     |
| 资产关联   | 已有资产登记、领借还、报废               | 报修引用真实资产；维修不会自动归还、报废或更换资产     |
| 待办与通知 | 已有统一待办及站内通知                   | 报修各环节按实际办理人产生待办，避免与普通任务重复     |
| 业务审批   | 已有采购、费用、付款审批                 | 日常报修直接受理；发生采购或付费需求时关联对应业务单据 |

现状依据：[工作事项契约](../baseline/work-items.md)、[资产契约](../baseline/assets.md)、[通用申请契约](../baseline/general-requests.md)、[待办中心接入](task-center-integration-design.md)。

## 2 目标与范围

### 2.1 首期交付

1. 员工提交电脑、外设、网络、办公软件、账号访问等故障，补充材料，跟进进度并确认结果。
2. IT 服务负责人分诊、调整优先级、指派和改派；工程师认领、处理、记录等待、提交解决结果。
3. 用户验收不通过时退回处理，保留原工单、时限及全部记录。
4. 支持响应与解决超时提醒、负责人升级、无有效处理人告警。
5. 提供本人列表、IT 队列、详情、流程视图和运营报表。
6. 接入统一待办、站内通知、附件、审计与现有业务权限。

### 2.2 首期边界

不包含远程控制、自动安装软件、自动重置密码、网络监控自动报障、供应商门户、备件库存、维修成本核算和完整 IT 配置管理。员工发现安全事件时应能标记并转交授权安全人员，但首期不承担安全事件调查系统的能力。

新设备采购、账号新增授权、付费软件订阅属于服务申请或其他业务审批；不能借报修绕过采购、权限或付款审批。首期允许 IT 说明正确入口并关联已有业务单据，未提供现有能力的事项保留线下办理记录，不显示为已自动完成。

## 3 角色与权限

| 角色          | 可见范围                                                   | 可执行动作                                                                       |
| ------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 报修员工      | 本人创建的工单及对本人公开的记录                           | 建草稿、编辑草稿或待补充内容、提交、补充、评论、申请取消、验收、评价             |
| IT 工程师     | 本服务组可领取的工单摘要；本人当前或历史参与工单的授权详情 | 认领、释放未开始任务、开始处理、公开回复、内部记录、申请等待、恢复、提交解决结果 |
| IT 服务负责人 | 被授权服务组的工单                                         | 分诊、优先级确认、指派、改派、退回补充、取消审核、合并重复单、管理异常及报表     |
| 系统管理员    | 配置与授权；业务工单需另有业务读取权限                     | 维护分类、服务组、人员及规则；不能默认代用户验收                                 |
| 安全处理人员  | 获明确授权的敏感工单                                       | 接收并处理转交事项；普通 IT 职责不自动包含敏感内容权限                           |

通用约束：

- 页面访问、动作、记录范围和字段权限分别校验，直接 API、详情 URL、附件下载和导出同样适用。部门经理身份不自动获得员工报修全文。
- 报修人默认取当前登录员工；首期不提供代他人报修。IT 帮忙登记需要员工本人提交，避免隐含代办权限。
- 内部记录仅授权 IT 可见，不出现在员工通知、导出、搜索摘要和附件列表中。普通公开附件与内部附件分别授权。
- 工程师只能操作当前分配给本人且仍有有效职责的任务；离岗、失去服务组资格后立即失去办理资格，负责人收到重新分派提醒。
- 报修人同时是工程师时，不得认领或处理本人工单；负责人应指派其他人员。无候选时保持待分派并告警，不自动结案。
- 只有报修人可以做用户验收；管理员结案是独立例外动作，必须标记，不能记录为用户验收通过。

## 4 入口与界面

### 4.1 员工端

- 在员工发起目录增加“IT 报修”，支持收藏、搜索和最近使用。
- “我的报修”支持按编号、标题、状态、分类、提交时间筛选；展示优先级、当前处理人、下一步、最近更新时间。
- 新建、补充、处理、验收等输入表单使用右侧抽屉，头部和操作区固定、正文滚动；复用现有表格、详情和状态组件。
- 详情按问题、进度、公开沟通、关联资产及业务单据组织。员工能明确看到“等待我补充”“IT 处理中”“等待我验收”。
- 提交前说明不要上传密码、验证码、密钥等内容；账号类故障填写账号标识及报错信息，不收集密码。

### 4.2 IT 端

工作区提供“待分诊、可领取、分配给我、等待中、待用户验收、已超时、已关闭”等筛选。列表显示分类、服务组、处理人、优先级及响应／解决期限；到期和超时分别提示，不能只靠颜色传达。

详情提供生命周期流程图、处理记录、内部记录和权限允许的动作。统一流程管理目录应能进入本流程定义和授权范围内的执行历史；业务参数配置有独立入口和权限，流程结构仍由代码定义。

### 4.3 通用体验

支持中英文；在 375px 宽度完成提交、附件、回复、验收和退回，无页面横向滚动。加载、无权限、空数据、失败和重试分别展示；提交中防重复点击，失败保留未提交内容。拒绝访问和加载失败遵循现有应用外壳约定。

## 5 工单信息

| 字段组       | 内容及规则                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 系统身份     | 工单 ID、提交后生成且唯一不变的业务编号、报修人、创建／提交时间、版本                                    |
| 问题标题     | 必填，去除首尾空白后 1–120 字                                                                            |
| 故障分类     | 必填，设备、网络、软件、账号访问、其他；停用分类保留历史名称，不能用于新提交                             |
| 问题描述     | 必填，1–5000 字；描述现象、发生时间、影响及已尝试操作                                                    |
| 影响程度     | 本人不能工作、本人部分受影响、多人受影响、业务中断；员工申报，IT 核实                                    |
| 联系与地点   | 办公地点必填，1–200 字；优先使用本人可授权读取的办公联系方式，也可填写本单联系方法，最多 200 字          |
| 故障发生时间 | 可选具体时间，不得晚于提交时刻；客户端和服务端均校验                                                     |
| 关联资产     | 可选一个主要资产；员工只能选择本人持有或被明确授权报修的资产；公共设备可不绑定资产并填写位置描述         |
| 故障附件     | 可选，单次及整单故障材料最多 10 个文件，每个不超过 20 MiB；支持图片、PDF、纯文本日志，后端验证类型与归属 |
| IT 分诊      | 服务组、确认优先级、影响范围、分诊说明；调整分类、组或优先级留前后值及原因                               |
| 处理记录     | 开始时间、处理动作、结果、处理人、公开／内部属性及附件；已提交记录只可追加更正，不能覆盖历史             |
| 等待记录     | 原因、责任方、下一次跟进时间、是否暂停解决计时、批准人及恢复时间                                         |
| 解决结果     | 原因分析、解决方案、完成说明各必填 1–2000 字，结果类型及可选附件；账号操作不保存秘密值                   |
| 验收评价     | 确认恢复或退回；退回说明必填 1–1000 字；确认后可选 1–5 星及最多 1000 字评价，不评价不阻止关闭            |
| 关联事项     | 重复主单、采购／费用单等引用；展示及跳转分别遵循来源单据权限，不复制受限金额和附件                       |

新建草稿允许业务必填项不完整；长度、文件及身份约束始终生效。提交时校验全部必填信息。提交后报修人只能追加公开说明或按要求补充，不能无痕改写原始故障。

工单还应保存部门和地点的提交时展示值、服务规则版本、优先级变更记录、首次响应时间、处理及等待区间、每轮解决／验收记录和关闭方式。时间点采用带时区时间，业务时限按公司工作日历计算。

## 6 流程状态与转换

### 6.1 标准流程

草稿 → 待分诊 → 待领取 → 已指派 → 处理中 → 待验收 → 已关闭。

分诊可直接指派而跳过待领取；IT 负责人也可以将尚未领取的工单退回员工补充。处理中可以进入等待，待验收可以因验收失败回到处理中。所有动作都校验当前版本和办理资格。

| 当前状态                       | 动作及角色       | 目标状态与要求                                                             |
| ------------------------------ | ---------------- | -------------------------------------------------------------------------- |
| 草稿                           | 报修人提交       | 待分诊；生成编号及服务时钟                                                 |
| 待分诊                         | 负责人要求补充   | 待补充；原因必填，不计为有效首次响应                                       |
| 待补充                         | 报修人补充提交   | 待分诊；沿用原编号、提交时间和响应时钟                                     |
| 待分诊                         | 负责人完成分诊   | 待领取或已指派；确认分类、组、优先级和公开处理建议                         |
| 待领取                         | 合格工程师认领   | 已指派；并发只允许一人成功                                                 |
| 待领取／已指派                 | 负责人指派或改派 | 已指派；目标人员实时有效，记录原因                                         |
| 已指派                         | 工程师开始       | 处理中；开始时间不等于解决完成时间                                         |
| 已指派                         | 工程师释放       | 待领取；仅尚未开始处理时允许，原因必填                                     |
| 处理中                         | 工程师申请等待   | 等待中；责任、原因及跟进时间必填，暂停计时另需负责人批准                   |
| 等待中                         | 当前工程师恢复   | 处理中；记录恢复事实和累计等待时间                                         |
| 处理中／等待中                 | 负责人改派       | 保留当前状态及既有时钟；等待中改派不自动恢复计时                           |
| 处理中                         | 工程师提交解决   | 待验收；完整解决结果必填，停止本轮解决计时，开始验收期限                   |
| 待验收                         | 报修人确认恢复   | 已关闭；记录用户验收及关闭时间                                             |
| 待验收                         | 报修人验收失败   | 处理中；原因必填，恢复累计解决计时，原工程师失效则进入待分诊               |
| 待分诊／待补充／待领取         | 报修人取消       | 已取消；原因必填，关闭待办，不删除记录                                     |
| 已指派／处理中／等待中／待验收 | 报修人申请取消   | 主状态不变，增加取消审核任务；工程师可继续处理，暂不允许提交解决或确认验收 |
| 有取消申请的非终态             | 负责人同意或拒绝 | 同意转已取消，拒绝清除取消申请并保持当前主状态；原因必填                   |
| 待分诊／待领取                 | 负责人标记重复   | 已取消；必须引用同权限范围内的有效主单并通知报修人                         |

取消申请不会暂停响应或解决计时；超时未处理要提醒负责人。取消审核与其他动作并发时，以版本校验串行提交，不得出现关闭后仍可批准取消。已取消、已关闭均为终态；不能通过普通编辑恢复。关闭后再次故障新建工单并引用原单。

### 6.2 例外结案

负责人可对非终态执行“管理结案”，需独立权限、原因和结果说明。关闭方式标记为管理结案，保留用户未验收事实；不计入用户验收通过量。不能以管理结案替代资产实际回收、采购完成或费用支付。

首期不因用户长期未验收而自动关闭；到期通知员工并升级 IT 负责人。负责人应联系核实或按管理结案处理。

### 6.3 处理结果分类

解决结果区分“已恢复”“提供替代方案”“转其他服务处理”。只有员工确认能够继续工作时才按用户验收关闭；无法修复而未获得员工认可时继续跟进或管理结案，不伪造修复成功。转采购、厂家维修或账号授权申请属于等待与关联事项，不自动视为解决。

## 7 分诊与办理规则

### 7.1 服务组与人员

首期至少配置一个 IT 服务组和一个负责人、两名合格工程师。分类映射默认服务组，负责人可按范围调整；找不到服务组或候选人时工单保留待分诊并通知服务管理员，不丢单、不自动批准。

工程师认领可领取工单时可看必要摘要；认领后才读取允许的完整材料。改派必须同一事务解除旧办理资格、建立新任务、写审计；旧页面即使保留按钮，操作也应失败并提示刷新。原参与人可在仍有记录读取授权时查看历史，但无当前办理权。

### 7.2 资产与费用

1. 报修不改变资产持有人、库存状态或折旧数据。设备维修中标记如首期需要，应作为单独服务状态，不覆盖资产现有领用状态。
2. IT 关联其他资产需具备相应资产范围权限；员工看不到的资产事实不得通过报修详情泄露。
3. 需要更换设备、采购配件或付费维修时，由有权限人员走既有资产／采购／费用流程，报修只保存关联和跟进记录。
4. 关联单审批通过不等于收到设备、支付成功或故障恢复。真实交付及付款仍由原业务服务提交；员工完成恢复验收后才正常关闭报修。
5. 关联单被拒绝或取消时提醒当前工程师，由其调整方案；不自动取消报修。无来源单据权限的员工只看到必要进展，不看到金额等受限字段。

### 7.3 重复、敏感与失效人员

重复单必须指向未取消、非自身且无循环关系的主单。主单和重复单均保留，员工可见的主单进度须单独授权；无权限时只显示“已关联统一处理事项”。首期不自动传播主单评论或附件。

敏感工单由负责人转交有权限的安全处理组，并收紧普通队列可见性。首期不承诺自动识别敏感信息；如现有权限能力无法保证隔离，应禁止普通报修上传敏感材料，并引导指定安全渠道，不能以隐藏按钮代替隔离。

报修人离职或账号失效后，不自动让其他人代为验收；负责人核实后管理结案或取消。人员失效不删除处理历史。

## 8 优先级与服务时限

以下为建议默认值，使用公司时区及工作日历；首期不承诺 7×24 值守。

| 优先级  | 判断建议                         | 首次响应目标 | 解决目标    |
| ------- | -------------------------------- | ------------ | ----------- |
| P1 紧急 | 多人关键业务中断，无可用替代方案 | 1 工作小时   | 4 工作小时  |
| P2 高   | 单人无法工作，或多人明显受影响   | 2 工作小时   | 8 工作小时  |
| P3 普通 | 局部故障且存在替代方案           | 4 工作小时   | 16 工作小时 |
| P4 低   | 轻微问题、不阻碍工作             | 8 工作小时   | 40 工作小时 |

- 员工申报影响程度；提交按建议映射暂定级别并立刻计时，IT 分诊确认。优先级变更需说明，对未完成指标应用新目标并从首次提交累计，不重置已消耗时间；已确认的超时事件保留。
- 首次响应是 IT 提交有效公开分诊意见，或工程师提交包含处理建议的公开回复。自动通知、认领、内部备注、单纯要求补充均不算首次响应。
- 响应计时从首次提交到首次有效响应，不暂停。解决计时从首次提交开始，待补充、排队、指派和处理中均计入。
- 等待中默认继续计时。仅等待员工配合、外部供应商、已关联采购或授权审批时，可由负责人批准从批准时刻起暂停解决计时；工程师忙、无人员、内部改派不得暂停。
- 等待必须设置下一次跟进时间，建议最多间隔 2 个工作日；到期提醒工程师和负责人。暂停时长和原因在报表中独立展示。
- 提交解决后暂停解决计时，另计验收等待；验收失败继续累计先前解决时长，不重新获得完整额度。总经历时长始终从首次提交到终态，包含全部等待和验收区间。
- 目标消耗达到 80% 时提醒当前责任人；到期未完成标记超时并通知负责人。恰好截止时刻仍未完成即超时。后续每天最多一次汇总提醒，直到指标完成。
- 待验收建议 2 个工作日内确认；超期提醒及升级，不自动验收。重复调度、重启和通知重试不能重复产生同一阶段告警。
- 提交保存规则和日历版本；配置修改只影响新提交工单。已有工单除显式优先级变更外保持原服务规则。暂停期间不得把没有当前截止时间展示成“未超时已达标”。

## 9 待办与通知

| 业务事件           | 待办归属                   | 站内通知                                                 |
| ------------------ | -------------------------- | -------------------------------------------------------- |
| 首次提交／再次补充 | 服务组负责人               | 负责人收到待分诊提醒；员工收到提交回执                   |
| 退回补充           | 报修人                     | 告知缺少什么材料                                         |
| 分诊后待领取       | 合格服务组工程师           | 服务组收到新单提醒，排除报修人本人                       |
| 认领／指派／改派   | 当前工程师                 | 新工程师收到处理提醒；员工看到进展；旧工程师收到移交信息 |
| 等待跟进到期       | 当前工程师                 | 工程师和负责人收到跟进提醒                               |
| 待验收             | 报修人                     | 告知处理结果及验收入口                                   |
| 验收失败           | 当前工程师或失效后的负责人 | 说明失败原因并恢复办理                                   |
| 申请取消           | 负责人                     | 原办理任务保留，增加明确的取消审核事项                   |
| 关闭／取消         | 无活动办理待办             | 通知报修人及当前工程师                                   |

报修是独立业务来源，接入公开任务中心能力；不把普通报修伪装成审批任务。不同时创建一张报修办理待办和内容相同的工作事项待办。个人发起跟踪如需接入，使用适合非审批来源的公开契约，不冒用 `approval.application`。

待办、人数、菜单脚标由业务事实更新；读通知不完成工单。待领取池工单可对多名合格工程师可见，但每人对同一工单只有一个可领取事项；认领后其他候选人的活动待办撤销。等待中保留工程师跟进事项，待验收移交给员工。本人申请跟踪不重复计入“待我处理”。

状态、待办及审计在同一事务提交，索引写入失败整体回滚。通知通过持久待发送记录重试，不因发送失败撤销已成功操作。消息只包含安全编号、允许展示的摘要及链接；点开后重新鉴权，不复制内部记录或敏感附件。

## 10 查询与报表

员工只能查本人有权查看的记录；IT 队列、搜索、导出和汇总应用同一服务组与字段范围。支持状态、组、处理人、分类、优先级、时间区间和超时条件筛选，结果分页；导出需独立权限并记录审计。

报表至少包含新增、当前未结、正常关闭、管理结案、取消、响应超时、解决超时、验收失败次数和等待时长。统计口径：

- 新增按首次提交时间；关闭按关闭时间；当前未结为查询时非终态存量，不能与区间新增简单相减。
- 响应达标率以区间首次响应已完成的工单为分母；解决达标率以区间用户验收关闭的工单为分母，取最终有效解决轮次累计耗时。两者均排除取消及管理结案，并另列仍未完成且已超时数量，避免只看完成单掩盖积压。
- 解决耗时为累计工作时长扣除批准暂停及验收等待；总经历时长包含所有区间。展示平均值、中位数及 P90，样本为零时显示无数据，不能显示 100% 达标。
- 解决达标依据最终累计时长判断，同时保留“曾超时”指标；改优先级不抹去历史超时事件。
- 满意度只统计真实提交评价的用户验收关闭单，同时显示参评数量及参评率，不将未评价当作满分。

## 11 一致性与可运维要求

1. 编号、工单状态、处理记录、任务分派和审计保持事务一致；失败不遗留半张工单或孤立待办。
2. 写动作使用请求标识及版本控制。同键同操作者同内容重试返回原结果；同键不同内容拒绝。前端请求标识沿用应用兼容内网 HTTP 的生成方式。
3. 两人同时认领、改派与旧人提交、验收与取消审核竞争时，最多一个版本成功；失败方获得刷新提示。
4. 附件按上传者、工单、用途及可见性验证；超量、伪造类型、其他单附件及无权限下载均拒绝。取消或关闭后历史附件仍受权限保护，不允许公开永久链接。
5. 操作审计记录操作者、动作、工单、前后状态、原因、时间、请求标识及必要字段变更；不记录密码或完整敏感日志。
6. 调度在重启后补扫未处理期限，按事件键去重。服务配置缺失、任务同步异常、连续通知失败有管理诊断入口。
7. 在隔离验收环境以 10 万张合成工单、50 个并发列表／详情读取作为建议性能基线；预热后查询 P95 不超过 2 秒，普通写入 P95 不超过 3 秒，不含文件传输与第三方耗时。记录硬件、数据分布和测量方法，不能以测试断言代替测量。

## 12 验收准备与执行方法

### 12.1 环境与账号

使用隔离 PostgreSQL 和专门文件存储，禁止写真实业务数据库。准备员工 A、员工 B、工程师 E1／E2、负责人 L、无业务权限管理员 S、其他服务组工程师 E3，以及一名具有明确业务例外权限的管理员。账号可以兼岗但基础用例先使用独立身份。

准备 A 持有资产、B 持有资产、公共设备说明、停用分类、失效工程师、可关联及不可读采购单、图片／PDF／日志、超大文件和伪装文件。全部使用合成数据，不含真实密码或个人资料。

固定公司时区 Asia/Singapore，使用明确的测试日历：周一至周五 09:00–12:00、13:00–18:00，无节假日；另建一个指定休息日测试例外。通过可控时钟验证时限，禁止等待真实数天或改生产时间。

每个用例先重置独立工单，记录初始版本、状态及活动待办；按步骤操作后同时核对界面、接口、业务事实、待办、通知及审计。权限用例必须直接调用接口，并检查列表、详情、附件和导出。预计失败的动作还需验证无副作用。

3. 员工 A、E1、L 分别在真实浏览器完成主流程和验收失败回路，并完成移动端核心路径。
4. 时限可由固定时钟重现；超时、暂停及例外结案在报表中可独立核对。
5. 性能基线有实测结果；未达标项和业务例外需业务负责人明确接受，不能标为全面通过。
6. 同步更新模块设计、需求基线、实施进度与审计记录；分别标识源码、注册、自动化、角色验收和发布状态。

## 14 首期建议与待确认事项

以下建议用于让需求可实施、可验证；确认前不视为公司现行制度，也不阻止本需求草案交付。

| 决策       | 首期建议                                            | 影响                                                |
| ---------- | --------------------------------------------------- | --------------------------------------------------- |
| 服务范围   | 公司内部 IT 故障，单一办公时区，可配置多个服务组    | 多地域值守需追加日历和责任转移规则                  |
| 受理方式   | 日常故障直接报修，采购／费用／授权另走已有审批      | 避免普通报修增加主管审批等待                        |
| 值守与时限 | 使用第 8 节默认值及公司工作日历                     | P1 如需夜间值守，应另定人力、通知渠道和 24 小时时限 |
| 验收关闭   | 用户确认后关闭；2 工作日催办，不自动关闭            | 避免无人验收被误记为修复成功                        |
| 费用与资产 | 关联现有业务单据，不自动发起支付或变更资产事实      | 需要更深联动时补单独接口及事务契约                  |
| 附件与保留 | 故障材料 10 个、单文件 20 MiB；首期无普通用户硬删除 | 数据保留和归档期限由公司制度确定，清理前另行设计    |
| 敏感事件   | 仅在权限隔离验收通过后开放安全组转交                | 否则保留独立安全渠道，禁止普通报修承载敏感材料      |
| 通知渠道   | 站内为首期必需；邮件及企业 IM 按实际启用状态扩展    | 外部渠道需独立联通验收，不假定已有开关开启          |

## 15 实施约束与参考

IT 报修由独立业务模块拥有状态和记录，复用生命周期、用户组织、授权、文件、待办、通知、工作日历和审计公共服务。是否复用工作事项内部能力由实施设计确认，但不得出现双份权威状态或直接写插件内部表。单纯用户确认不要求引入一条审批流；付费、采购等沿用已有业务 owner。

迁移采用增量且不可修改已发布历史；验证使用隔离 PostgreSQL。保存实际时间点使用 `datetimeTz`，服务日历保留日期及当地工作时段语义。客户端使用现有请求标识和 API 客户端约定。
